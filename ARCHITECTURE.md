# Architecture

How a task moves through Branchlog. When this flow changes, update this file.

The window and the database are two processes. They never touch each other. A small bridge sits between them.

## What you see

The window is a React page (the renderer). The open day lives in one store, `useNotebook`. The page reads tasks, the date, focus, and errors from that store.

The daily page is one canvas. The main list is a single node. Each branch is its own node, tied to its parent by `parentId`. Those nodes are a view of the store. They do not keep their own copy of the task. A branch node looks up its task in the store by id.

The window shows one view at a time: the daily canvas or the activity calendar. The open view lives in a small store, `useView`. The Go menu item "Calendar", the menu in the top bar, and the `show-calendar` menu action open the calendar; Escape, the Back link, or clicking a day returns to the daily canvas. The calendar is a GitHub-style grid of the last 53 weeks. A day is active when at least one task has that day as its `dateCompleted`. The counts come from one read-only query over `tasks`, fetched each time the calendar opens. Clicking a day opens that day on the daily canvas. The grid is drawn on screen only; it saves nothing.

## What is saved

The Electron main process owns a SQLite file, `branchlog.sqlite`, in the app's user-data folder. It is the record of every task. The renderer cannot open that file. On startup the main process copies it into `backups/` once per day and keeps the last seven copies. Window size and position are a separate file, `window-state.json`, next to the database.

## How a change moves

The preload script is the only bridge. It puts `window.branchlog` on the page. The page calls that. Preload forwards the call to the main process, which checks the payload and then reads or writes SQLite. The result comes back the same way.

Opening a day flushes any text or position still waiting, then loads that day's rows and replaces the store's list. The load is one round trip (`tasks:listByDate`) that returns the day's tasks and its AI comments with their replies together (`DayLoad`); comments are never fetched one task at a time. If you have already moved to another day by the time the rows arrive, those rows are discarded.

Creating a task or a branch waits for the database. The store shows the row the database returned, so the page cannot show a task that was rejected. The page creates the id.

Branching from an earlier day writes a new main-list task onto today and leaves the earlier task unchanged. The new task keeps that earlier task as its parent. The daily page does not draw an arrow for that link. It shows a dot to the left of the checkbox. The dot's words are the parent row's text and date, read when the day opens and held on the store for that day only. They are not written back. The Go menu item "Branch from an earlier task", and Ctrl or Cmd+K, search tasks dated before today and use the same write. A branch from a task on today, or on a later day, still grows to the right on that day's page.

Editing text, or dropping a branch in a new spot, updates the store right away. The write to SQLite waits a short moment and is sent once. Dragging does not write. The canvas holds the moving position until you let go, and only then does the store record it. Resizing a branch works the same way: the new width, height, and position are recorded when you let go, and that write waits the same short moment. A pasted image resizes from its corners with its aspect ratio kept. When you let go, the store records the new size and position and one write saves that image's row right away, the same way a dropped image saves its position. An image file can also be dragged from the file manager onto the canvas. The page reads the dropped file's bytes and sends them over the bridge, where the main process decodes them and saves the image exactly like a paste. A drop or paste that is not an image shows an error on the page instead of doing nothing. A selected image can also be cropped from its four sides. The crop is non-destructive: the row keeps four fractions (`cropLeft`, `cropTop`, `cropRight`, `cropBottom`) of the full picture that are trimmed away, and the page renders the visible part by offsetting the image inside its frame. Dragging a side shrinks the node's box and grows that side's fraction; letting go saves the box and the fractions through the same image row write, and one undo restores them. The saved PNG file is never rewritten.

When auto-separate is on, a create, a drop, a resize, a text reflow, or a pasted image can glide overlapping branch and image rectangles apart. Main-list rows stay where they are. The glide is drawn on the canvas only. When it stops, one layout commit writes every moved position. That commit is part of the history entry for the action that caused it, so one undo restores the action and the positions together. The setting lives in `settings` under `autoSeparate` and is on when that row is missing. Trackpad scrolling lives in `settings` under `swipeToPan` and is on when that row is missing. On, a wheel or a two-finger swipe pans the daily canvas, and a pinch or Ctrl (Windows and Linux) or Cmd (macOS) held while scrolling zooms it. Off, the wheel zooms, which is the older behavior. Panning and zooming change the viewport on screen only. They do not write to SQLite. The canvas recenters when the day loads. Pasted images are rows in `images`, and the file is `userData/images/<id>.png`.

The open theme lives in `settings` under `theme`. It is one JSON document: the light palette, the dark palette, whether to follow the system, the chosen mode, and named presets. The preload reads that row once, synchronously, and writes a style tag before the first paint. Later edits change those CSS variables on the document. They are not React state. The write back to `settings` waits a short moment, the same way task text does. Theme Lab's own undo stack is separate from task undo.

The AI settings live in `settings` under `ai`, one JSON document: on/off, the LM Studio base URL, an optional model name, the daily comment cap, and the pause delay. The AI margin panel (File > Settings > AI margin, or Ctrl/Cmd+,) reads and writes it through `ai:settings` and `ai:setSettings`; it is off until the user turns it on, and a successful Test connection turns it on. Test connection asks the main process (`ai:testConnection`) to GET `{baseUrl}/models`; the renderer never makes that network call itself. `lm-studio.ts` in the main process is the only module that talks to LM Studio: it lists models and posts chat completions with a timeout and abort support, and falls back to asking for JSON when the server rejects structured output. Nothing calls LM Studio at startup.

With AI on, a pause in typing can earn one margin comment. The trigger lives in the renderer (`lib/ai-trigger.ts`, installed by `lib/ai-trigger-install.ts`): it waits the pause delay, requires changed text of at least twelve trimmed characters on an open main-list task, and never sends the same text twice for one task. It asks the main process through `ai:requestComment`; the main process re-checks the task and the daily cap, builds the prompt (`ai-prompts.ts`: the task, up to five ancestors, and a capped list of the day's other main-list tasks — never images or other days), and posts one chat completion. Only one automatic request is in flight; a newer one aborts the older, and a reply that arrives for text the task no longer has is discarded. The model's JSON answer is parsed defensively (`ai-parse.ts`); a null, malformed, or oversized answer writes nothing and stays silent. Only a connection failure shows the quiet offline note. A saved comment is a row in `aiComments` (always `side = 'left'`) and comes back to the page, which draws it as a draggable canvas node left of the main list, with an arrow to the task's bullet. The AI never edits task text. While a request is in flight the task shows small thinking dots that take no layout space. If the server cannot be reached, the page shows one quiet status note, not an alert.

A comment can be answered ("Write back..."), resolved to a reopenable dot, or deleted. A reply goes through `ai:reply` (a second, separate in-flight slot), saves the person's reply and the model's answer as two `aiReplies` rows in one transaction, and returns the fresh comment. Resolve and reopen use `ai:setCommentStatus`; delete uses `ai:deleteComment` and is one undo entry. Comment positions save once after a drag, through the same layout commit as branches and images; one commit carries task, image, and comment points (`layout-save.ts`). Comments take part in collision avoidance as pushable bodies; the main list stays fixed.

Checking a box updates the store, then waits for the database. If that write fails, the store puts the old value back and shows an error. A failed text save is tried once more, then the store shows an error.

Closing the window sends any waiting text and positions immediately.

Undo keeps a short history of the open day in the renderer. It is a list of earlier rows, not a second notebook. Changing the day drops that history. Undo and redo write the restored rows back through the bridge, including a full replace of that day's tasks when a task was created, deleted, moved, or checked.

Deleting a task removes that task and every descendant, on every day, in one database transaction. AI comments, replies, and concept-map positions are removed with those tasks by foreign keys. Edges are drawn from `parentId` and disappear with the tasks. Images are not attached to a task, so a delete does not remove them. The undo entry keeps the removed tasks, including ones from other days, their concept-map positions, and their AI comments with replies and kept ranges. Undo writes that set back (`ai:restoreComments` re-inserts the rows); redo deletes them again. A comment-only delete is also one undo entry; its undo and redo replace the open day's comment rows through `ai:replaceComments`. Resolve and reply are not undo entries. For about eight seconds the page shows "Deleted N tasks. Undo", and that button uses the same undo as Cmd/Ctrl+Z.

An unfinished task can also be carried onto today. That is a different link from a branch. The original row stays on its day. The new row is a copy: `carriedFromId` points at the previous copy, and `chainId` is the id of the first copy in that chain. A task that was never carried has `chainId` equal to its own id. An insert that leaves `chainId` blank is filled with the new row's id. `droppedAt` is the day the task was dropped. A dropped task is not carried, and dropping one task does not drop its branches. Open, done, dropped, carried, and superseded are read from those columns and from whether a later copy exists. They are not stored.

Carry-over runs in the main process, in one transaction, and only for today's date. It runs when the app starts, when a window focuses, when the computer wakes, and at the next local midnight. The on/off switch and the number of days are `settings` rows: `autoCarry` (on when the row is missing) and `carryWindowDays` (14 when the row is missing). One run is one undo entry. Undo deletes the copies that run created. Deleting a copy relinks the next copy so its `carriedFromId` points at the deleted copy's previous link, and it does not delete the other copies. Undo of that delete writes those links back. A startup run that would copy more than a few hundred tasks waits until the first paint, then the page receives the new rows. A smaller run is written before the window opens.

## One owner for each fact

The database owns saved tasks. A task's `dateCreated`, `dateCompleted`, and `droppedAt` are local calendar keys (`YYYY-MM-DD`), the same shape as the open day. `chainId` and `carriedFromId` belong to that same row. The store owns the open day. A continuation's parent text and date belong to the parent task. The store keeps a copy of those two fields for the open day so the dot can name them, and the next day load replaces that copy. The write queue (`pendingText`, `pendingPosition`, and the branch size queue) only remembers what still needs to be saved. Today's key is not stored: `now()` and `localDateKey()` in `src/shared/dates.ts` compute it from the local year, month, and day. The page title reads that key again at the next local midnight, when the window focuses, and when the computer wakes. The main process tells the page about a wake on `clock:resume`. Moving between days uses `addDays`, which steps the calendar date. The canvas owns a position only while you are dragging it, and a branch's size only while you are resizing it. Edges are drawn from `parentId` and are not stored. The caret and the "frame this page" callback are momentary and are not saved.

`x` and `y` on a task are its place on the daily page. `width` and `height` are the branch node's size there. A height of 0 means the branch is as tall as its text. The main list ignores both. The database also has tables for AI comments, replies, images, concept-map positions, and settings. The daily page reads `images`, the day's AI comments and replies (in the same load as the tasks), the `autoSeparate` setting, and, when a carry-over run finishes after the page is open, the copies from that run. `autoCarry` and `carryWindowDays` are read by the main process. Concept-map positions are still unread. The open day's comments live in one store, `useAiComments`; a comment node looks its row up there by id, the same way branch nodes read tasks. `aiComments.x` and `y` are the comment's place on the daily page, owned by the database like a task's position. Each table stays the owner of its rows, and concept-map positions stay in `mapPositions` rather than in the task's `x` and `y`.

## Where the code lives

- `src/main` — window, menu, security, backup, validation, IPC, and the database. `database.ts` opens SQLite and runs the day-to-day queries. `continuation.ts` writes a task onto today from an earlier parent, lists those parent links for a day, and searches tasks dated before today. `day-sync.ts` replaces one day's rows when undo needs the saved tasks to match the page again. `task-tree.ts` deletes a task with its descendants and restores that set. The delete and the restore live in `task-delete.ts`, which also relinks `carriedFromId`. `carry.ts` copies unfinished tasks onto today, drops and undrops a task, and reads the derived state. `carry-schedule.ts` runs that copy at startup, on focus, on wake, and at the next local midnight. `schema.ts` holds the notebook tables. `migrate.ts` rebuilds an older tasks table so a parent delete cascades, adds `width` and `height` when those columns are missing, adds the carry columns and backfills `chainId`, then once removes tasks whose parent row is already gone. `images.ts` stores a pasted image, stores a dropped image file from its bytes, saves a resized or cropped image's box and crop fractions, and lists the day's images. `migrate-images.ts` adds the crop columns to an older images table. `layout-save.ts` writes the positions from one settled separation. `settings.ts` reads and writes `autoSeparate` and `swipeToPan`. `theme-store.ts` reads and writes the `theme` settings row. `ai-settings-store.ts` reads and writes the `ai` settings row, and `lm-studio.ts` is the LM Studio client. `ai-store.ts` owns the `aiComments` and `aiReplies` queries (list for a day, insert, reply pair, status, delete, restore, replace). `ai-comment.ts` orchestrates one comment or reply request: eligibility, the daily cap, the single in-flight slot with abort, the stale-text guard, and the insert. `ai-prompts.ts` holds both system prompts, the JSON schemas, and the context builders with their caps. `ai-parse.ts` parses the model's JSON answer defensively. `ai-validate.ts` checks every AI IPC payload. `migrate-ai.ts` adds the `type` and `keptRanges` columns to older tables. `src/shared/theme.ts` is the token list, the default palettes, and the checks on that row. `src/shared/ai-settings.ts` is the AI settings shape, its defaults, and its checks. `src/shared/ai-comments.ts` is the comment and reply shapes, the result unions, and their type guards.
- `src/shared/separate.ts` — the rectangle separation used by the daily canvas. It does not touch React or the database.
- `src/preload` — the bridge, and nothing else
- `src/renderer` — the React page, the store, and small helpers
- `src/shared` — types and date helpers used by the other three. `dates.ts` owns today's key, and `clock.ts` is the only `now()`. A development build, and the build `npm test` produces, read `BRANCHLOG_NOW` there. A production build replaces that file with `clock-off.ts`, which always uses the real time.
- `tests` — Playwright tests that launch the real app against a temporary data folder. `mock-lm-studio.ts` is a local HTTP stand-in for LM Studio with scriptable answers; AI tests never use a real model.
